适用版本：v2.41.x（含 R79 角色边界、R80 任务持有权、R81 记忆归属、R82 撤销/复核署名、R83 任务/租约署名、R84 通信署名、R85 闭环署名、R86 待审批队列、R87 审批时效、R88 交接老化、R89 交接作废、R90 拦截可观测、R91 治理查询索引、R92 CLI 管理面补齐、R93 治理面巡检、R94 桌面治理可见性、R95 跨面一致性回归、R96 桌面待审批操作面、R97 桌面交接操作面、R98 状态页审批积压、R99 安全拦截按 agent 聚合、R100 审批退回、R101 追加型写入署名、R103 接入参数漂移巡检、R105 用量异常巡检）。所有命令默认在 AgentHub 源码目录执行；`<root>` 指大脑根目录（如 `D:\agent资料\zcode项目记录`）。

## 0. 五分钟体检

```bash
python cli.py init --root <root>          # 新目录先建脑：目录结构+库，幂等不覆盖；目录须已存在
python cli.py --root <root> doctor        # 全项巡检，逐条给修复建议；有问题退出码 1
python cli.py --root <root> doctor --full # 展开完整修复口径与全部明细（默认只列失败类别与前 3 条）
python cli.py doctor --root <root>        # --root 写在子命令前后都行（R226）
python cli.py doctor --root <root> --json # 单行 JSON（给脚本/agent 读，不用啃中文）（R237）
python cli.py doctor --only env,ghost_memory --slow 8  # 只跑白名单项 + 强制出耗时榜（R237）
python cli.py doctor --no-machine         # 摘掉机器级项，只看当前根目录（R237）
python cli.py check --list                # 看全部检查项，标出哪些需要 --target（R237）
python cli.py check deploy_diff --target <本源码目录>   # 跑单项（含 patrol 覆盖不到的 17 项）（R237）
```

不想开终端：GUI「设置 → 系统自检 → 运行自检」跑的是同一套巡检检查（后台执行、显示逐项进度、失败项给修复口径、报告可一键复制）。

报告里的「机器级」项（运行进程 / 全局 agent 配置）与当前根目录无关——换 `--root` 也会照实报，不要当成新库坏了；`runtime_health` / `rules_health` 属于这一类。

如果首条是「大脑库不存在」，后面的库依赖项会合并成一条「同因跳过」（如 `13 项同因跳过`），不会每项各报一遍修复手册——按首条的修复行建库或指对根目录后重跑即可（R233）。

`doctor` 默认只显示**非零问题类别**及对应的修复动作，避免一次铺出十几项全量治理口径；需要完整上下文时加 `--full`。耗时榜默认只在总耗时超过 3 秒时出现（GUI 报告里单项 ≥1s 也显示同一榜单），想在小耗时下也看榜单就加 `--slow N`；榜里的百分比分母是**本次实跑项的耗时之和**，不是墙钟（R237）。体检全程不加载语义编码模型：泄漏探针走词法/BM25/图路，语义路只做结构性计数（R230，真实库全检 11.8s→3.2s）。陈旧记忆的「已取代条目还会不会被检索吐出来」判定，从**5 条关键词抽样**换成**全量结构判定 + 1 条金丝雀**（R248）：四条候选通道（LIKE/BM25/图补/语义）全部只从 `WHERE <_live_sql>` 取候选、融合层只删重排序不添行，所以「已取代行能通过存活谓词的数量」就是泄漏上界——一条 SQL 全量查（真实库 22 条 0.9ms），再拿最新那条已取代记忆真跑一次检索确认接线没断（`semantic=False`/`gate=False`，一次 28ms）。判定更快也更强：真实库 `stale_health` 热态 154.3→41.4ms，覆盖从 22 条里的 5 条扩到 22/22；模拟存活谓词回归时旧实现报 5 条、新实现报 22 条。检索的**图扩展路原来每次检索都全表重建邻接表**（真实库 `relations` 2725 条 7.7–7.9ms），而两跳遍历真正读到的只有「种子 + 第一层」的边：改成按层定向取边（`_graph_edges_touching` / `_graph_local_adj`，最后一层只留对端为目标类型的边）后 1.9–2.7ms，一次检索 52.8→46.0ms、`search_all` 的跨类型增强 9.4→1.6ms、`stale_health` 20.9→17.4ms；分数与排序和旧实现**逐位一致**（以旧源码对拍 650 组 0 差异），`_graph_adj` 保留给图谱统计/聚类（R249）。BM25 通道的打分原来对**每篇文档的全部词表**统计 df（记忆 5.5ms、记录 25ms，占打分 99%），而 df 只在 query 词上被读：改成只统计 query 词后，`_bm25_rank` 9.8→4.8ms、`_records_bm25_rank` 42.5→14.6ms（−66%）；再叠加「窄列取行 + 只对 top-k 回表取全列」，`search_memories`（`semantic=False`/`gate=False`）28.8→24.3ms、`search_records` 111.4→88.4ms（−21%），输出全字段与顺序和旧源码对拍 0 差异（R250）。检索的**语义第三路**每次把 1575 条活跃记录的全列（含 971KB content）连同 3.3MB 向量一起拉回，而余弦过 0.58 门槛的只有 0–11 条：改成先窄取 `eid+vec` 算余弦（0.11–0.19ms）→ 过阈值排序截 limit → 只对这些 id 回表取全列（仍带存活谓词，两查之间被取代的行只消失不复活）后，`_semantic_rank`（records）28.4→19.7ms、`search_records` 中位 93.9→87.8ms，输出与旧源码对拍 0 差异（R251）。本机代理探测上限 100ms——FlClash 没开时不会让每次体检白等一秒（R234，env 1.0s→0.1s）。幽灵候选扫描（`ghost_memory`）的分词与两两求交换成「整型位集 popcount」，真实库 6.8 万对 448ms→77ms、单项 1.03s→0.41s，逐对结果与旧实现完全一致（R235，全检 2.4s→1.7s）。检索的覆盖度闸门原来**每个查询词发两条全表 COUNT**（16 词就是 32 次全扫，单次检索 34–82ms），现在改成每表一次 `SUM(content LIKE …)` 条件聚合、并与语料总量共用同一条连接：真实库一次检索 75→54ms、`stale_health` 602→471ms、全检 1.8s→1.6s；文档频率逐词与旧写法全等，同时补齐了旧实现承诺却没做的「只算活跃行」——被取代/作废的行不再给 df 加分（R236）。语义检索模型加载时不再向终端打进度条。

机器可读与单项入口（R237）：`doctor --json` 输出一行 JSON（`schema`/`root`/`asked`/`filters`/`slowest`/`report`，`report` 就是 `run_patrol` 的原样返回，`slowest` 按 `name`/`ms`/`share` 排好），退出码仍是「有问题 1、没问题 0」，脚本不用再解析中文。`--only`/`--skip`/`--no-machine` 用来裁范围：白名单只认 `doctor` 巡检清单里的项，顺序**永远跟随注册表**（先验库再看环境），不受你书写顺序影响；`--no-machine` 摘的就是 `MACHINE_CHECKS` 那几项机器级检查。**拼错的检查名是用法错误，不是跳过**——点名报出、退出码 2、一次巡检都不跑；把「静默忽略」当省事其实是漏报，比误报危险。同理，`--only` 里出现「注册表里有、但巡检清单不跑」的项名（如 `hygiene`）也会被点名并让你改用 `cli.py check hygiene`，不会被悄悄丢掉只跑剩下那几项。需要 target 的检查走 `cli.py check`：`cli.py check --list` 现读注册表并逐项标出要不要 `--target`（`py_compile`/`git_status`/`regression`/`deploy_diff`/`release`/`ponytail_gate`/`coverage_gate`/`stdout_guard` 这类都在这批里，只有 patrol 会跑的检查项一律免 target）。手册不写注册表条数——数一数就会漂，以 `--list` 为准。`check` 对需要 target 的项**刻意不设默认值**——在部署副本上跑 `deploy_diff` 就是自己比自己，必然全绿；target 不存在同样退 2 而不是给出「检查发现问题」的结论，两类码不能混。

等价 MCP：`hub_sentry(action="report")`（只出报告、不广播）；日常哨兵用 `hub_sentry()`（发现问题广播给所有 agent）。

体检项：环境 / 运行版本 / 数据库 / 备份 / 规则闸门 / 陈旧记忆 / 幽灵记录 / 重复记忆 / 记录四段式 / 日期格式 / 任务治理 / Inbox / 停滞项目。

## 1. 工具全部消失或客户端连不上

按顺序排查：

1. **进程是否活着**：`python cli.py status`；客户端里 MCP server 显示 failed/红点即未启动。
2. **stdout 污染**（最常见）：MCP stdio 下任何 `print` 都会让 JSON-RPC 解析失败，表现为工具全没了。检查进程加载模块里是否有控制台输出；`hub_ops_run(name="stdout_guard", target=<目录>)` 可扫描。
3. **配置路径**：每个 agent 的 MCP 配置应指向部署目录 `~/.agenthub/mcp_server/agenthub_mcp.py`（或源码 `agenthub_mcp.py`）。改完配置需重启客户端。
4. **版本/协议**：`python cli.py call hub_health` 能通说明服务端正常，问题在客户端握手；检查 `initialize` 是否返回 `protocolVersion`。
5. **限流**：单工具 600 次/60s、单 agent 2000 次/60s（环境变量可调，`AGENTHUB_RATE_LIMIT=off` 关闭）。被拦是业务错误 `isError`，不会断连。

## 2. 部署了但没生效（跑的是旧代码）

```bash
python cli.py deploy                              # 源码 → ~/.agenthub/mcp_server
```

`runtime_health` 会点名「进程加载的代码落后于磁盘」的文件。两条途径：

- 在 agent 会话里经 MCP 调用：`hub_ops_run(name="runtime_health")`、`hub_agent(action="status", agent="<名>")`；
- CLI / `doctor`：R24 起会读取运行中 MCP 进程落盘的**运行标记**（`~/.agenthub/runtime/serve-<pid>.json`，30s 心跳、120s 过期），据此给出「一致/需重启」并注明「观测来源：心跳中的 MCP 进程」。

CLI 自己仍不是在跑的服务进程（`python cli.py call …` 会导入模块但只活几秒）。**没有新鲜标记时**它诚实返回「无法判断」——这通常说明各 agent 的 MCP 进程还没重启到 v2.40.93+，不是故障。**重启各 agent 的 MCP 进程**后新代码才生效，标记也会随之出现；只 deploy 不重启等于没发。判定基准是进程加载时的指纹与启动时刻，心跳只刷新标记文件的 mtime，不会把旧代码洗成一致。标记按不可信输入校验：坏 JSON、空目录、不可解析或未来的启动时刻、非字典指纹都会被忽略（未来时刻曾可伪造「一致」），不会让体检崩溃或给出假结论。进程被强杀留下的旧标记会由下一次服务启动或超过 20×TTL 的清理逻辑移除。

`hub_agent(action="verify")` 的验证快照绑定的是**当前进程加载代码的源码指纹**（md5，不是 mtime），所以「部署了但没重启」会让快照当场标为过期——这是正确行为，不是误报。重启后再 verify 一次即可。快照同时记录**代码树**（源码目录 / 部署目录）：从另一棵树（例如 CLI 导入源码树）复查时显示「无法据此判断」，不会把另一棵树多出的文件误报成过期；在 agent 会话里重跑 verify 即绑定部署树。

## 3. 备份、校验与恢复

### 3.1 备份

```bash
python cli.py --root <root> call hub_export action=backup
```

产物：`<root>/_hub/backup/brain-YYYYMMDD-HHMMSS.zip`，内含：

- `brain.db`：用 sqlite 官方 backup API 取的一致性快照（含 WAL，**不是**文件复制）；打包前先跑 `PRAGMA quick_check`，不通过即放弃并清理临时文件
- `_AgentHub_备份清单.txt`：生成时间、跳过文件/目录数量与原因
- 其余为备份时刻的项目文件树：排除构建/缓存/依赖/备份目录（`build*`、`dist*`、`node_modules`、`.venv`、`backup` 等），单文件 >50MB 跳过（`AGENTHUB_BACKUP_MAX_FILE_MB` 可调，0=不设上限）

可靠性：先写同目录临时文件，成功后 `os.replace` 原子改名——中途失败不留半成品、也不会覆盖已有备份；同一秒内重复备份自动追加序号。

### 3.2 盘点与校验

```bash
python cli.py --root <root> call hub_export action=backups
python cli.py --root <root> call hub_export action=verify path=<zip 路径>
python cli.py --root <root> backup-drill [备份路径]        # 恢复演练，留空=最新整包
```

四类备份：`zip` 整包 / `legacy_db` 旧版仅库 / `snapshot` 在线快照（`_hub/brain-backups`，自动轮转）/ `manual_bak` 手工 `.bak`。

`verify` 会读取包内清单、对库快照跑 `quick_check`，并输出记录/记忆/项目/文件数与跳过统计；末行「完整性 ok」才算通过。

`drill`（R61）比 `verify` 更进一步：把备份里的 `brain.db` 解到临时目录、按恢复流程打开，报告核心表计数、schema 版本、包内最新流水时效与所需空间，并与现场库对比——「现场比备份新」会点名恢复将丢掉多少写入。不写现场数据、不碰 `-wal/-shm`；R75 起成功后会在审计流水留一条「备份演练」痕（「可恢复性上次被证明是什么时候」从此可查，提醒周期 30 天）；坏包、缺 `brain.db`、没有备份分别给出可执行错误。**备份能通过 verify 不等于能恢复；上线新流程前至少跑一次 drill。**

### 3.3 清理（默认只预演）

```bash
python cli.py --root <root> backup-prune              # 预演：只列候选，不删
python cli.py --root <root> backup-prune --apply      # 真删：保留各家族最新 N 份 + 7 天内不动
```

安全线：主库 `brain.db`、`-wal`、`-shm` 永不碰；只删四类备份模式命中的文件；删除写 journal 可追溯。首次建议先看预演结果。

### 3.4 恢复（手工，先停写）

**预备（R61）**：`python cli.py --root <root> backup-drill [备份路径]` 确认包「可用于恢复」；若出现「现场比备份新」或「数据量不同」，说明恢复会丢掉备份之后的写入——先决定是否先补一份新备份再动手。

1. **停掉所有 agent / GUI**，确认没有进程再写 `<root>/_hub/brain.db`。
2. 保留现场：把当前 `brain.db` 改名为 `brain.db.before-restore-YYYYMMDD`；把 `brain.db-wal`、`brain.db-shm` 移走（恢复后由 SQLite 重建）。
3. 解压备份到临时目录，取其中的 `brain.db` 放回 `<root>/_hub/brain.db`。
4. 项目文件按需恢复：zip 里的文件树是备份时刻状态，**整树覆盖会冲掉更新的工作**——只挑丢失的文件恢复。
5. 校验：`python cli.py --root <root> call hub_health`；GUI 打开确认记录/记忆条数正常。
6. 回滚：停写 → 把 `brain.db.before-restore-*` 改回 `brain.db` → 重启。

### 3.5 库损坏的识别与降级（R59）

SQLite 文件损坏时（断电、磁盘故障、杀进程写坏），所有查询会抛 `DatabaseError: database disk image is malformed`。现在的降级口径：

- **CLI**：`tasks/digest/...` 不再吐堆栈，统一给「大脑数据库文件已损坏」+ 库路径 + 恢复步骤，退出码 **2**；`call` 子命令遇到 `isError` 一律退非零（此前失败也退 0）。
- **MCP**：协议层返回 `isError=true` 与同一份恢复指引，`structuredContent` 带 `db_corrupt: true`；**不会再写「已记入大脑错误」**——库读不了时 `error_add` 必然失败，假成功比报错更危险。
- **体检**：`hub_ops_run(name="db_integrity")`（`PRAGMA quick_check`）。`python cli.py doctor` 会把它排在第一项；坏库时其余检查标为「数据库损坏，跳过」，避免一屏次生失败。

识别只认文件结构损坏（`malformed` / `not a database` / `file is encrypted`）；`database is locked`、`no such table` 等不算损坏，仍按各自路径处理——**别误恢复备份**。

处置顺序：停写 → 留证（`brain.db`、`-wal`、`-shm` 三件一起复制，WAL 里可能有未落盘数据）→ `hub_export action=backups` 选最近整包并用 `action=verify` 校验 → **`action=drill` 试恢复**（确认「可用于恢复」、schema 与数据量正常、恢复会丢多少写入）→ 按 §3.4 手工恢复 → `doctor` 与 `db_integrity` 复核。

```bash
python cli.py --root <root> call hub_ops_run name=db_integrity
python cli.py --root <root> doctor
```

## 4. 任务管控：看板、租约、依赖与追溯

多 agent 共用同一块看板，四件事必须可判定：谁在干、是否还活着、这单卡在哪、接手后旧进程还能不能写。

### 4.1 看板与流转

- **看板**：`hub_tasks`（可按 status/project/owner 过滤）与 `hub_next`（前沿队列：可认领/进行中/可接管/等待）。每行行尾自动标注：截止紧迫度（已逾期/今天/临近）、前置进度 `n/m`、不存在的前置 `⚠前置不存在 #id`、残留阻塞、租约状态、进展停滞。
- **流转**：`hub_task_update(task_id, status=…, blocked_by=…, priority=…, deps=…, due=…)`。让任务从阻塞恢复时传 `blocked_by="-"`；重排截止日传 `due="YYYY-MM-DD"`，取消截止传 `due="-"`——**只有显式传 `-` 才清空**，缺省不动该字段（避免「改状态顺手抹掉截止日」）。看板上 `blocked` 状态却无阻塞原因的残留标记会标注「可清除」。
- **认领**：`hub_claim(task_id, agent)` 单条原子抢单；同一 owner 再次认领=续租，不重复写开工锚点。
- **谁能领活（R36–R38）**：`hub_agent(action="control", state="draining")` 让 agent 收尾不接新活（active 正常 / draining 收尾 / paused 暂停 / offline 离线）；`hub_agent(action="skills", skills="python,文档")` 声明能力，任务用 `skills="python"` 声明所需技能，双方都声明才按交集过滤（未声明=放行，兼容存量）；每人同时在办上限默认 3（`AGENTHUB_MAX_WIP` 可调，0=不限），续租不占新名额，完成/释放即腾位。认领、改在办、交办共用同一组闸门。
- **交办（R39）**：`hub_task_update(task_id, agent="当前持有者", handoff_to="目标", handoff_note="做到哪了")`。目标须在册、active、技能匹配且未到 WIP 上限；换主前先写检查点，成功后释放任务名下文件租约、给对方发「【交办】」信号并写 journal。管理面可省略 `agent` 直接交办。

### 4.2 租约与自愈

- 默认 2 小时（`brain.CLAIM_TTL_HOURS`）。心跳、`hub_task_update`、`hub_checkpoint` 都会续租。
- 超过 2h 未续租可被他人接管；**无主（无 owner）或缺失租约的在办任务也可以被 `hub_claim` 接管**（自愈），不再永久卡死。
- **撞车**：`hub_heartbeat` 会列出同项目他人持有的在办任务（含租约是否过期）。

### 4.3 依赖图（DAG）

- `deps` 用逗号分隔任务编号；前置未全部完成时任务不进前沿、不可认领。
- 自依赖与成环会被直接拒收，错误文案给出完整环路径（`#a → #b → #a`）；允许引用尚未创建的未来任务 id（正向规划）。
- 前置 id 写错或指向不存在的任务时，等待段显示「前置不存在 #id」；`tasks_health` 会连同自环、缺失前置一起点名。

### 4.4 检查点围栏与迟到写入

`hub_checkpoint(action="save", task_id, content)`：在办任务只收持有者的写入——非持有者拒收且不落行；写入成功同事务续租。任务被接管后，旧持有者因条件更新 `rowcount=0` 被拒，不会污染新持有者的进展时间线——这道写入围栏正是「租约决定谁能干、围栏决定迟到写入无效」的分工。

**进展停滞（R26）**：租约/心跳只证明持有者在线，不证明任务在走。推进口径是独立列 `progress_at`（认领/流转/改详情/写检查点会写，**心跳不碰**）加最新手工检查点；超过 `TASK_PROGRESS_STALL_HOURS`（默认 6h，= 3×租约 TTL）无推进即「进展停滞」。看板/控制面/GUI 显示 `⚠进展停滞 Nh`，`tasks_health` 单独计数；停滞与「持有者失联」互斥（先判失联），**只点名不自动释放**。修法：写 `hub_checkpoint(action="save", task_id=…, content=…)` 记录真实进展，或由持有者 `hub_task_update` 流转/更新后继续。

**时间口径（R27）**：四个钟各管一件事，谁都不能冒充谁——**推进**（任务级，`progress_at` 加手工检查点，只有真实任务动作会写）、**检查点**（任务级断点，认领锚点不算）、**心跳**（agent 级存活，取持有者最近一次 `sessions.ts`，不代表任务在走）、**租约**（还能不能被接管）。`tasks.updated` 会被心跳续租刷新，因此历史里只作「最后改动」展示；它与推进不一致时，时间线会另列一条「最后推进」。`hub_history(kind="task", id=…)` 头部给出一行四钟时刻，`hub_agent status` 的持有摘要列出推进/检查点/心跳（标注 agent 级）；`hub_list_agents` 只保留推进以维持单行密度。

**记录↔任务闭环（R35）**：写工作记录时传 `task=任务编号` 把这条记录绑定进任务闭环：

```text
hub_log_work(project="AgentHub-多agent文件统一管理", agent="zcode", task=2,
             content="目的：…做了什么：…验证结果：…如何回滚：…")
```

- 绑定前校验任务存在且项目一致（写错任务号会污染结晶与巡检，直接拒收）。
- 持有者写入 = 一次真实推进：顺带续租并刷新 `progress_at`；**绑定不等于认领**，pending/blocked 任务不会被记录顺手开工。
- 记录里写了「已完成/已交付/关单」但任务还没 done 时，写回执当场告警；`hub_status` 与 `hub_ops_run(name="tasks_health")` 会列为「完成声明未关单」。核对后 `hub_task_update(task_id=…, status="done")` 关单即消失；负向表述（尚未完成/未交付）不计。
- 待审批积压也进 `hub_status()` 的「在办任务」之后（R98）：显示条数、待批过久数、最久等待与前 3 条（owner/项目/等批时长/`hub_task_approve` 入口），与 `hub_tasks(view="approvals")` 同口径；开工对齐不必再查第二处。
- 任务完成结晶优先收编绑定记录（不受创建时间窗限制），并排除属于其它任务的同项目记录；结晶正文分列「任务绑定 N 条 + 同项目同期 M 条」，结晶自身也绑定该任务。
- 历史未绑定记录：正文点名「任务 #N」且含完成声明的，同样纳入漂移巡检。

**完成质量（R40）**：`hub_task_update(task_id=…, status="done")` 回执会附完成质量分数与提示（不阻断完成）；`hub_task_quality(task_id=N)` 单查，`hub_task_quality(days=7)` 巡检近 N 天完成的任务（分数升序，最差先看）。检查项：人工检查点、绑定工作记录、交付物核验、关闭说明、认领后 2 分钟内且无人工检查点的「极速关单」。自动开工锚点与结晶记录**不算**过程痕迹——它们只证明开过工/系统收过尾，不证明人做过事。评分是提示不是 KPI：低分先核对是不是占位任务或漏写记录。

### 4.5 任务过程控制：取消 / 重试 / 延后 / 审批（R41–R45）

任务不是只有「做」和「做完」——放弃、失败重来、暂时不做、交付复核都需要留下可追溯的痕迹，而不是把任务删掉或静默搁置。

- **取消（R41）**：`hub_task_update(task_id, status="cancelled", cancel_reason="为什么取消/替代方案")`。原因必填；终态不可逆（要继续请新建任务，别用复活抹掉取消原因）；释放任务文件租约并退出队列/WIP。`hub_tasks --status cancelled` 可回看取消原因。
- **失败重试与死信（R42/R43）**：`hub_task_retry(task_id, reason="接口 502", delay=可选秒数)`。原因必填；任务放回待办并指数退避（默认 60s×2^(n-1)，上限 1h，`AGENTHUB_RETRY_BASE` 可调），`hub_next` 单列「退避中」；连续失败达上限（默认 3，`AGENTHUB_MAX_ATTEMPTS` 可调）自动进入**死信 `dead`**：退出队列、保留持有者供追溯、通知持有者，再调一次 retry 即复活（次数重置）。`delay=0` 表示确认修复、立即重排。
- **延后（R44）**：`hub_task_update(task_id, defer_until="2026-11-01", defer_reason="等上游接口")`。日期按当天 00:00 恢复；任务退出前沿（不算待办饥饿），但在 `hub_tasks`/`hub_next` 的「延后中」段可见；到点自动回到可认领。提前唤醒传 `defer_until="-"`。在办任务只有持有者或管理面可延后；延后会释放 owner、任务文件租约并清掉退避。
- **完成审批（R45）**：`hub_task_add(..., approval_required=true)` 开启后，任务标 `done` 前必须由**他人**复核：`hub_task_approve(task_id, agent="复核人", note="验收依据")`。four-eyes——owner 不能给自己批准；管理面批准走 CLI：`python cli.py --root <root> approve <task_id>`（**进程锁定的会话里空传 agent 会被顶成锁定身份**，R70 dogfood 实测，R71 起拒绝文案会当场点明这条）。批准只对本次完成有效，`approval_required=false` 会清空旧批准。
- **待审批队列（R86）**：`hub_tasks(view="approvals", project=可选, limit=可选)` 直接列出在办、已开启审批、尚未批准的任务，按认领时间升序（等最久的先看），附持有者/最近进展/截止/租约等看板注解。只读视图；批准仍走 `hub_task_approve`（owner 不能自批）。
- **审批退回（R100）**：复核不通过用 `hub_task_reject(task_id, agent="复核人", reason="哪里不合格、怎么改")` 退回返工——**原因必填**，owner 不能自退（与批准同 four-eyes，管理面走 CLI：`python cli.py --root <root> reject <task_id> --reason "..."`）。仅对 `in_progress` 且未批准的审批任务生效；退回即释放 owner/租约/文件锁回 `pending`，`rejected_by/at/note` 与 `reject_count` 留痕（看板显示↩退回次数/退回人/原因），owner 收到退回信号，修改后重新 `hub_claim` 再次进入审批队列。已批准的任务不能退回——如验收有误，在 detail 记问题并新建返工任务。
- **审批时效（R87）**：队列每行显示「等批 X 小时/天」（从**认领时刻**起算；缺认领时间显示「等批 —」，不硬造数字），达到 `TASK_APPROVAL_AGING_H`（默认 24h）标「⚠待批过久」。同一口径进入 `tasks --stats` 的「待批过久」计数、团队日结的当前卡点与 `approval_aging` 风险/建议。它只是**复核实提示，不是硬 SLA**：先看最近进展——还在施工就催进度/改期，真在等批就批准或退回说明。
- **项目交接与老化（R88）**：`hub_handoff(action="create", project, agent, done, next_step, excluded)` 留下 typed 交接上下文；`action="list"` 显示待认领时长，open 超过 `HANDOFF_STALE_DAYS`（默认 3 天）标「⚠陈旧」；`action="claim"` 原子认领（仅一人成功）。时间缺失/不可解析显示「时间未知」，不硬造天数；已认领不误标陈旧。`hub_status(now)` 与团队日结的「交接 N（陈旧 X）」同口径；陈旧交接风险会进 `handoff_stale` 建议。
- **交接作废（R89）**：废弃的未认领交接用 `hub_handoff(action="close", handoff_id, agent, close_note)` 关闭——`close_note` 必填（原因进 journal），只允许 `open` 状态；已认领的交接不可作废（接手已发生，不能抹掉认领人），要终止请新建交接或发信号说明。重复关闭幂等，回显原操作者与原因，不覆盖首次记录。`list(include_claimed=True)` 显示「已作废，谁于何时：原因」；已作废不可再认领。close 与 create/claim 一样纳入署名闸：MCP 会话必须 `--agent` 锁定身份，未锁定拒收并记「越权拦截」。

### 4.6 文件租约（防「不同任务改同一个文件」）

任务租约只解决「谁干这单」，解决不了「两个人各干各的单、却同时改同一个文件」。`hub_lock` 是**建议性（advisory）**占位：不拦截文件写入，只让冲突在动手前可见——不阻断编辑器/脚本，也就不会误伤。

```text
hub_lock action=check   path=src/core.py                    # 只读查占用
hub_lock action=acquire path=src/core.py agent=zcode task_id=12 reason="改租约重入"
hub_lock action=renew   lease_id=7 agent=zcode ttl_min=60   # 或 action=acquire 同路径同主
hub_lock action=release lease_id=7 agent=zcode              # 或 path=... 释放自己在该路径的全部租约
hub_lock action=prune   limit=200                           # 回收过期未释放（只标记释放，活跃不碰）
hub_lock action=list    project=AgentHub-多agent文件统一管理
```

- **冲突口径**：同路径、以及祖先-子孙目录（锁 `src/` 与锁 `src/a.py` 互斥）都算冲突；相对根/绝对路径/`~` 均可，比较时统一 `normcase` + 正斜杠，Windows 大小写不敏感。
- **TTL** 默认 30 分钟（1~480 封顶）。过期租约可被他人接管，接管时该路径 `fence` 单调 +1——迟到写入可用它自证「我拿的是旧票」。
- **任务绑定**：传 `task_id` 时要求任务在办且持有者是调用者。任务完成/退回/换主/被接管会**自动释放**任务名下全部租约；绑定租约随心跳自动续，**未绑定租约不自动续**（防止忘了释放造成死锁）。
- **预警**：心跳列出同项目、其他 agent 持有的文件租约（含剩余分钟/任务/理由）；`hub_tasks`/`hub_next` 行尾显示 `锁 N`。
- **审计**：获取/续租/释放/任务级释放均写入 journal，`hub_history(kind="task", id=…)` 可见同一任务的全部占位轨迹。
- **巡检**：`hub_ops_run(name="lease_health")` 点名活跃冲突、任务绑定漂移（任务已完成/换主却没释放）、持有者未登记；过期未释放只报数供清理（它不拦人，不算失败）。
- **回收**：过期未释放用 `hub_lock action=prune`（或 `cli.py locks --prune`）一键回收——只标记 `released_by='expiry'`、记录保留（fence 仍是迟到写入的对照凭据），活跃租约永不触碰，重复调用幂等。
- **headless**：`python cli.py locks [--project X] [--owner A] [--path P]` 看台账/查占，`cli.py lock <path> --agent A [--task-id N]` 获取，`cli.py unlock <id> --agent A` 或 `unlock --path P --agent A` 释放，`cli.py locks --prune --agent A` 回收过期。

### 4.7 控制面与追溯

- `hub_agent(action="status", agent=…)` 与 `hub_list_agents` 显示每人持有的在办任务及租约状态；无主在办任务单列，提示可接管。控制面默认给「推进 Nh 前」，`hub_agent status` 额外列出检查点与心跳（标注 agent 级）。
- `hub_history(kind="task", id=任务编号)`：合并 journal 流转、检查点时间线、任务卡关键时点（创建/认领/完成），复盘「这单一路上怎么变成现在这样」。头部「时间口径」一行给出推进/检查点/心跳/租约四个时点，「最后改动」不等于进展。
- `hub_ops_run(name="tasks_health")`：过期租约/无主/持有者失联/进展停滞/逾期/依赖结构异常/交付物证据不全/完成声明未关单一次点名，只报不动手。
- `hub_ops_run(name="governance_health")`（R93）：把「等人拍板」的积压收成一张单子——待批 ≥24h、open 交接 ≥3 天、近 7 天未锁身份拦截（配置漂移）、角色越权 ≥3 次（反复试探；1-2 次只提示）。与 `tasks_health` 分工：那边看任务/租约本身，这边看管理动作是否积压。只读；修复走 `hub_task_approve` / `hub_handoff claim|close` / 核对各 agent 的 `--agent` 启动参数。`doctor`/`hub_sentry` 的巡检清单已包含此项。
- `hub_ops_run(name="mcp_drift")`（R103）：接入参数漂移的事前检测（governance_health 的「未锁身份拦截」是事后信号）——配了 agenthub 但 args 配错的入口当场点名：`--agent` 被删（该 agent 会被 R82-R101 署名闸持续拦写）、锁名与注册名不符（归属分裂）、server 脚本路径失效（MCP 起不来）、`--root` 指向别库（写入目标分裂）。漂移行优先展示；修复按 detail 提示改配置后重启该 agent 的 MCP 会话。
- 桌面「大脑」页任务看板对租约过期、进展停滞、逾期任务打徽标；待批任务显示「待批 Nh」，超过 24h 用警示色并标「待批过久」（R94）。
- 桌面「治理中心 → 安全与闸门」页直接展示 `governance_health` 结论与明细（R94），有积压时页摘要转警示态。
- 桌面「治理中心 → 待审批」页按等批时长排序列出待批任务（R96）：显示 owner/项目/等批 Nh/最近进展与「⚠待批过久」；选中后点「批准完成」可填复核意见，署名桌面管理面 `gui`，批准后队列即时移除；owner 不能自批（four-eyes 由 `brain.task_approve` 强制，拒绝原因原样提示）。
- 桌面「治理中心 → 待认领交接」页按创建时间倒序列出 open 交接（R97）：显示来源/项目/已等时长/下一步与「⚠陈旧」（≥`HANDOFF_STALE_DAYS` 天）；「认领交接」以 `gui` 署名（恰一次），「作废交接」必须填原因；勾选「含已认领/已作废」可复核接手人与作废原因；已认领交接不可作废由 brain 强制。

```bash
python cli.py --root <root> tasks --approvals                 # 待批队列：等最久优先，标 ⚠待批过久
```

```bash
python cli.py --root <root> handoffs --close <id> --reason "…" --agent reviewer
python cli.py --root <root> security [--days 7]               # 越权拦截：按工具/按 agent 聚合 + 身份/角色分类
```

- `tasks --approvals` 与 `hub_tasks(view="approvals")` 同源（`brain.task_approvals`），等批从认领起算，缺时间显示「未知」不硬算。
- `handoffs` 默认只列 open；`--all` 含已认领与已作废。`--close` 走 `brain.close_handoff`：原因必填、仅 open 可关、已认领拒绝（接手已发生）、重复关闭幂等回显原操作者。
- `security` 与 `hub_status(view="security")`、`digest` 同口径（`brain.security_snapshot`）；输出按工具与按 agent 双聚合（R99），桌面「治理中心 → 安全与闸门」同页展示；`--days` 1..365，超界报错退出非零。
- 三条都是管理面直连（等同 CLI 管理员通道），不受 MCP 署名闸影响；但它们**不绕过**任务状态机与角色规则，作废交接仍要求操作者署名。
- 跨面一致性有 e2e 守卫（R95）：`tests/e2e/test_cross_surface.py` 在同一个库上比对 MCP 会话、CLI 与 `governance_health` 的队列/老化/陈旧/拦截口径，并跨面验证「MCP 作废→CLI 可见」「CLI 批准→MCP 队列消失」；怀疑各处数字对不上时先跑这条用例。

### 4.9 任务过程统计（R53）

看板回答「有哪些活」，统计回答「队列在流动吗、卡在哪、谁在拖」：

```bash
python cli.py --root <root> tasks --stats --days 7
python cli.py --root <root> tasks --stats --project AgentHub-多agent文件统一管理
```

MCP 同口径：`hub_tasks(view="stats", days=7, project="…", owner="…")`。

- **流量**（窗口）：新建 / 完成 / 取消或死信 / 审批通过。
- **完成周期** = `done_at - created`，报中位、P90、最长；长尾用分位看，别被均值骗。
- **在办**（当前快照）：租约超时、无主、等审批、逾期——每条都给出可处置动作（`hub_claim` / `hub_task_approve` / `hub_task_update`）。
- **重试存量**：多少单失败过、累计次数、最高次数；`retry_storm` 风险提示重试 ≥2 次的在办单。
- **完成质量**：抽检窗口内最近 30 条完成单（不是全量慢查），给出达标/告警/均分；`agent` 过滤时跳过（质量巡检按项目维度）。
- **风险信号**：租约超时、无主、等审批、逾期、死信、重试风暴，带 `#id` 样例。

口径差异写在输出末尾：流量/周期/质量是窗口口径，在办/重试/风险是当前快照；审批耗时是 `approved_at - created` 的近似值（任务表没有申请时刻）。

### 4.10 团队日结与 agent 记分卡（R55）

任务统计看「过程」，日结回答「这段时间谁做了什么、现在该谁处理什么」。一条命令把窗口流动、当前卡点、风险归因、处置建议和按 agent 记分卡放在一屏：

```bash
python cli.py --root <root> digest --days 1
python cli.py --root <root> digest --days 7
```

MCP 同口径：`hub_status(view="digest", days=1)`（`days` 1..365；默认 `view="now"` 保持原状态页不变）。

- **流动**（窗口）：记录 / 记忆 / 任务新建·完成·取消或死信 / 错误新开与未闭 / 工具调用 / 检索与零命中；完成周期给中位数。
- **当前**（快照）：在线 agent、在办总数与租约逾期 / 无主 / 等审批 / 逾期四项卡点、写入冻结状态。
- **风险归因**：租约逾期、无主、等审批、逾期、无心跳但有在办、死信、重试 ≥2、未闭错误、零命中检索。每条带 `#id` 样例、责任人（空归属单列）和一句可执行建议（`hub_claim` / `hub_task_approve` / `hub_error_close` 等）。
- **按 agent 记分卡**：在线/控制状态、窗口内记录与活跃天数、记忆、任务新建/完成/在办、未闭错误、调用与检索、个人风险标签；按在办→记录→调用排序，只列窗口内活跃或有在办的 agent。
- **归因口径**：`owner`/`agent` 统一小写去空格（`Qoder` 与 `qoder` 合并）；空归属不硬塞给某个 agent，而是在「无主在办」风险里单列。
- **只读**：日结不写 `searches`，不改变任务状态；建议只是建议，动作仍由持有者/管理面执行。

与 `hub_status()` 的分工：`now` 看此刻（谁在线、今天变了什么），`digest` 看一段时间的团队产出与欠账；与 `hub_tasks(view="stats")` 的分工：后者只看任务过程，日结还包含记录、错误、调用与 agent 记分卡。

### 4.11 全脑检索的覆盖范围（R56）

`hub_search` 与桌面搜索页现在检索六类：工作记录、记忆、随记、任务、错误登记、文件名（另加 `hub_search_files` 的 Everything 全盘段）。任务与错误同样带 `#id`，可直接继续用 `hub_tasks` / `hub_list_errors` 精读。

- **任务检索**：多词 AND，跨标题/详情/项目/负责人/最近错误；排序为在办 → 阻塞 → 待办 → 完成 → 终态（同状态按优先级、id 倒序）——先看正在处理的活。
- **错误检索**：多词 AND，跨标题/详情/agent/项目/回滚方式；未关闭条目优先，已修复条目保留回滚方案供复用。
- **计数与截断**：`hub_search` 头部同时给出六类命中数；行数超限只截断展示，不改变 `log_search` 记录的命中总数。
- **桌面**：搜索页分类下拉新增「随记 / 任务 / 错误」；任务/错误预览含状态、负责人、截止、最近错误或回滚方式，支持复制与跳转项目。
- **边界**：任务与错误只做词面 LIKE（不走 BM25/语义/图增强），因此关键词要带具体词；`limit` 参数沿用 `search_all` 的 30（任务/错误各自上限 100）。

### 4.12 流水页错误处置（R57）

错误登记的处置动作都在桌面「流水·错误与流水」页：

- **筛选**：`全部 / 未关闭 / 已修复`，旁边显示当前条数与其中未关闭数；筛选项只影响展示，不改变数据库。
- **详情**：选中一条即在下方预览完整标题、状态、登记人/时间、项目、详情与回滚方式（列表里只显示回滚前 60 字）。
- **复制回滚方式**：一键复制 `undo` 字段，直接粘到终端；没有登记 `undo` 时提示让上报者用 `hub_report_error(undo=…)` 补齐。
- **按钮启停**：标记已修只在未关闭条目上可用，重新打开只在已修复条目上可用，打开项目/复制需选中且有对应字段；刷新或状态流转后按错误 `#id` 保留选中。
- **双击**：等价于「打开相关项目」。

排查提示：`open` 堆积说明修完没关（`hub_error_close` / 页面「标记已修」）；已修复条目保留回滚方案，下次同类故障可直接复用。

## 5. 检索质量回归

```bash
python tools/eval_search.py                     # 当前库：MRR / Hit@1/3/5 / weak / 耗时
python tools/eval_search.py --records           # 记录侧
python tools/eval_search.py --root <冻结语料根>  # A/B 同一语料（防跨天数据漂移冒充回归）
```

输出会打印语料规模（memories / records 条数），**报告指标时必须带上规模**。冻结语料做法：用 sqlite backup API 把 `_hub/brain.db` 复制到临时根的 `_hub/` 下。评测 `count_hits=False`，不污染唤起统计。

**持久冻结语料（R76 起）**：`output/eval-corpus-20261023/`（16MB，records 1457 / memories 328，含 `manifest.json` 记录冻结时点、规模与当时指标）。跨轮复测直接 `python tools/eval_search.py --root <项目目录>/output/eval-corpus-20261023`，与 manifest 的 expected 对账；语料过期（规模差 >10%）就重新冻结一版，不要拿新语料对旧基线。

### 5.1 规模与内存（R60）

- **BM25 分词缓存**：进程内 FIFO 上限 4 万条（约 80MB；`AGENTHUB_TOK_CACHE_MAX` 可调，0=不限）。语料超过上限时**不缓存**、每次重新分词——逐条淘汰会让每条检索反复分词，实测把 3 万条的 0.3s 拖成 5.7s。
- **覆盖度闸门**复用已算好的 df，不再为拉丁乱码判定二次全表 COUNT。
- 大库实测（3 万记录 / 1 万记忆）：`search_all` 单词 ~0.29s、多词 ~0.57s、长中文串 ~0.64s；`team_digest` ~0.03s。规模继续变大时优先保证内存有界，检索变慢属预期。

## 6. 发布与桌面 exe

```bash
python tools/bump_version.py --check   # 版本自检：SERVER_INFO / README / CHANGELOG 首行是否同版本
python tools/bump_version.py 2.41.82   # 递增：先在 CHANGELOG 写好 | v2.41.82 | 首行，再一条命令同步其余两处并复检
build.bat                        # 构建前 build-manifest start，打包后 finish + 复制桌面 + release 自检
python cli.py release            # 单独复查：产物 sha256 / 构建后源码哈希 / 桌面副本 sha256
python tools/smoke_exe.py        # 双击的那份 exe 真能出窗口：标题+稳态内存+退出残留+配置不动
```

- **冒烟判据四条缺一不可**（R236 从一次性脚本升为常驻工具，判据逻辑有单测守着）：窗口标题出现（进程数与窗口句柄都早于「界面可用」，只按进程数判会假绿）、主进程内存进入稳态平台（半加载态实测 77MB vs 就绪 268MB）、`taskkill` 后残留进程为 0、用户 `~/.agenthub/config.json` 的 md5 前后不变。

- **顺序铁律：先提交 → 再构建 → 再发布**。构建清单的 `git_head` 是打包那一刻的 HEAD，`dirty` 是那一刻工作树是否脏；先构建后提交会让清单指向一个不包含自己源码的提交（v2.41.78–v2.41.98 连续 20 个版本踩过）。构建之后不许再改/提交任何仓库文件。

- **发布溯源闸门（R241）**：`cli.py release` 见清单 `dirty=true` 直接失败；`publish.py` 另加四条——清单可读、清单版本 == 要发的版本、`dirty` 必须明确为 `false`（旧清单没记 `dirty` 也拒）、`git_head == 当前 HEAD`，且 `--exe` 的 sha256 必须等于清单产物（防把旧构建挂到新标签下）。默认只预演打印闸门，加 `--yes` 才真的调 GitHub API。

- **GitHub 发布节奏（R241 起）**：每轮收口只 `git push origin main` + 注释 tag，**不建 Release**；Releases 隔几个大版本发一次（跨 ≥5 个 patch 或一条主线收完）。发布时跑 `HTTPS_PROXY=http://127.0.0.1:7890 python publish.py --yes`——本机 TUN/系统代理下 `urllib` 不读系统代理，不给 `HTTPS_PROXY` 会 `WinError 10060`。token 只从 `GITHUB_TOKEN`/`GH_TOKEN` 读（经 GCM 取），不落盘、不回显。`publish.py` 尚在 `.gitignore` 里，属本机发布工具，不入仓库。

- **版本号单一来源是 `agenthub_mcp.py` 的 `SERVER_INFO`**；README 与 CHANGELOG 首行必须跟随（`adv_mcp.py` 与 `tests/unit/test_tool_docs.py` 双重看守）。历史教训：R204 只改了 SERVER_INFO（CHANGELOG 断档），R216–R220 三次递增都漏了 README，所以递增一律走 `bump_version.py`，不再手改。

- 桌面副本：`%USERPROFILE%\Desktop\AgentHub.exe`
- 构建清单：`dist/AgentHub.build.json`（文件名来自常量 `ops.BUILD_MANIFEST`，与 `build_manifest` 函数同名不同物——按「build_manifest.json」找会找不到）；`start` 段快照 35 个输入的 md5（根目录运行时代码 + `pages/` + 图标），`finish` 段记 exe 的 sha256
- `release` 三处任一不一致即失败；无清单时回退 mtime 并明示可能误报
- onefile 启动需解压，首次启动慢属正常；已排除文本嵌入用不到的视觉栈
- `deploy` 先全量复制到暂存目录并逐文件校验，成功后整目录原子换入；复制中断时旧部署原样保留（不会出现半新半旧模块）

改完源码后：先 `python cli.py deploy` 让 MCP 面生效，再 `build.bat` 让桌面 exe 生效。**其他 agent 的 MCP 进程需重启**，否则仍跑旧代码。

## 8. 错误分类与重试

工具失败时看 `structuredContent.error_kind`：

- `transient`：限流/库锁/资源忙 → 退避后重试（只认原因词；文案里出现「请重试」不构成暂时性证据）
- `permanent`：参数非法/目标不存在/越权/键冲突，以及**执行前闸门**（身份未锁/非 manager/全局冻结/确认闸/项目绑定不符/幂等键复用）→ 立即失败，改条件重发
- `ambiguous`：超时/结果未知 → **不要盲重试**，先只读查询确认状态；仅 `hub_log_work` / `hub_note` / `hub_memory_write` 声明了 `idem_key`，这三个可用同一键幂等重放（其它写工具传了会被当未识别参数提示）

写工具支持 `dry_run=true` 预演；需人工批准时传 `confirm=false` 返回 `input_required`（不执行、不阻塞服务端），批准后带 `confirm=true` 重发执行。

## 9. 调用归属与使用观测

`hub_usage_timeline(view="stats", days=7)` 的「归属覆盖」行回答「控制面数据里有多少调用能追到人」：

- **有主**：`--agent` 进程锁定（最可信）> 写工具显式 `agent`（中）> initialize `clientInfo`（低，仅补已注册客户端）。
- **空**：客户端既没锁 `--agent`、也没自报可识别的 clientInfo。空归属高通常说明该 agent 的 MCP 配置缺 `--agent`，或仍在跑升级前的旧进程。
- **历史空行不回溯**：归属在调用发生时就已落库，事后无法可靠推断；修好配置并重启客户端后，新调用才会带主。

排查顺序：① `python cli.py status` 看该 agent 的 MCP 启动参数是否含 `--agent <注册名>`；② 重启客户端使新配置生效；③ 再跑 stats 确认「空」停止增长。筛选类工具（`hub_agent`/`hub_tasks`/`hub_usage_timeline`）的 `agent` 参数是「查谁」，不会被当作调用者。

## 10. 安全与审计（防篡改、冻结、取证）

这一组回答四个问题：**记录有没有被改过、出了事能不能一键刹车、安全面现在干不干净、出了事拿什么给别人看。**

### 10.1 审计链：证明「没被改过」

`journal` 每条在写入时封存 `prev_hash` + `hash`（sha256 覆盖 agent/action/target/backup/note/前后时间），链头记在 meta `journal_head`。

- `hub_ops_run(name="audit_chain")` 或 `python cli.py call hub_ops_run name=audit_chain`：通过时也报「已封存 N 条 / 封存起点」，**没爆红不等于开了**——先看封存数是否为 0。
- `hub_audit`：按人/动作/关键词查流水，输出末尾附导出命令。
- 判定口径：改字段、删行、换序、截断链尾都会点名 `#id`；封存前的历史行只能证明「封存后未改」，报告里单列 `legacy` 条数。
- 链断了怎么办：**不要重算哈希掩盖**。先用导出留证，再查权限与进程，修复后从证据链尾部重新封存；`audit_chain` 的修复建议里写明回滚/追权限路径。

### 10.2 全局写入冻结：出事时的一键刹车

```bash
python cli.py freeze --minutes 30 --reason "迁移中避免并发写"
python cli.py freeze --minutes 0 --reason "长维护，手动解冻"   # 手动挡，不会自己到期
python cli.py freeze --off                                      # 幂等解除
python cli.py freeze                                            # 只查看状态
```

MCP 侧同名能力：`hub_freeze(action="status"|"freeze"|"off")`；桌面在「治理中心 → 安全与闸门」点「冻结写入」（分钟 + 原因必填）。

- 生效范围：**所有写工具**在 `call_tool` 入口统一拦（跨进程，不是某个客户端的约定）；读工具照常可用。
- 豁免：`hub_freeze` 自己（否则解不了冻）和 `hub_undo`（撤销是收敛动作，冻结期间仍应放行）。
- 到期自动解除；meta 里的冻结值损坏时**按冻结处理（fail-closed）**，宁可拦住也不放行——状态无法确认时放行等于没闸门。
- 冻住期间写调用返回明确原因与解除命令，不会假装成功。

### 10.3 安全面体检 `security_health`

`hub_ops_run(name="security_health")`（CLI：`python cli.py call hub_ops_run name=security_health`）一张单子看五件事：

1. 审计链完整性（复用 10.1 的判定）；
2. 当前是否处于写入冻结（是信息项，不算失败）；
3. agent 管控状态是否合法（非法值会被点名，不会静默跳过）；
4. 在办任务（in_progress）的 owner 是否还能解析到已注册 agent——孤儿任务会指出 id；
5. 记录/记忆/随记/错误里的明文凭据扫描：OpenAI 风格 `sk-`、GitHub `ghp_` 等、AWS `AKIA`、私钥块、`password=...` 赋值。**只报位置，不回显密钥**；`os.environ.get(...)`、示例占位符不误报。

命中凭据时正确处置是**轮换密钥并改走环境变量**，不是只删记录——记下来那一刻已经泄露。修复建议里有轮换路径。

**成本与口径（R247）**：扫描前先按「任何模式命中都必需的字面量」过筛（`sk-`/`ghp_`/`AKIA`/`-----BEGIN` 与 password 一类关键词），只能跳过**不可能命中**的文本，判定与逐条跑正则逐字相同（真实库 2027 条过筛 13%，正则 118.6→26.1ms）。另：**一次全量巡检只验一次审计链**——`audit_chain` 与 `security_health` 同批共用同一次校验（同一次 `doctor` 里两项报出的封存条数一致），单项 `check` / `hub_ops_run` 仍每次真验。

### 10.4 审计导出（取证/交接）

```bash
python cli.py audit-export --format jsonl --days 30
python cli.py audit-export --format csv --days 7 --limit 5000
```

MCP 侧：`hub_export(action="audit", audit_format="jsonl", days=30, limit=20000)`；桌面在「治理中心 → 安全与闸门」点「导出审计」，链异常会在提示里点名。

- 落盘到 `<root>/_hub/exports/`，原子写（临时文件 + rename），不会留下半截文件。
- JSONL 首行是 meta（导出时间、范围、截断标记、导出时的链快照），之后每行一条 `journal` 或 `op_audit`；CSV 为扁平列（`utf-8-sig`，Excel 直接打开不乱码）。
- **链异常时照导**，meta 里标 `chain.ok=false`——取证场景不能因为库不干净就不让导出；但导出不会「修好」链，别把导出件当清白证明。
- `truncated=true` 表示触到 `limit`，缩小 `days` 或调大 `limit` 再导。

### 10.5 项目名护栏

`project` 会参与目录定位与筛选，所以统一校验：禁止 `..`、`/` `\`、盘符、控制字符、保留名（`_hub`、`00_Inbox`、`99_Archive`、`projects`）与以点/空格结尾。覆盖 `hub_log_work`、`hub_task_add`、项目归档/恢复、Inbox 移动、`hub_create_project`。

校验是**宽松的**：不强制「对象-问题」命名，历史项目名与临时标签照常可用。被拒时返回原因，直接改名重试即可，不要绕过。

### 10.6 角色边界：谁可以动刹车（R79）

控制面工具不再对所有人开放。`agents.role` 只有两档：

| 角色 | 能做什么 | 默认 |
|---|---|---|
| `worker` | 日常读写：记录、记忆、任务、信号、租约、检查点、只读查询；读自己的角色；管自己的控制状态/技能 | 是（含历史存量） |
| `manager` | worker 全部能力 + 冻结/解冻、项目归档/恢复、记忆隔离/合并、自动化开关、清理备份、管控他人 | 否 |

**管理通道隐式 manager**：桌面 GUI、`python cli.py …`、REST 直连不走 MCP initialize，视为本机管理员操作，不受角色限制。MCP 会话（stdio server）按启动时 `--agent` 锁定的身份查 `agents.role` 判定。

```bash
python cli.py role                      # 列出所有 agent 角色
python cli.py role qoder                # 看单个
python cli.py role qoder --set manager  # 授权管理动作
python cli.py role qoder --set worker   # 收回
```

MCP 侧：`hub_agent(action="role", agent="qoder")` 只读；设值需调用方是 manager 或走管理通道。**agent 不能自我提权**：worker 调 `action="role"` 改自己同样被拒。

会被拦下的典型动作（MCP 会话 + worker）：`hub_freeze(freeze/unfreeze)`、`hub_archive_project`、`hub_quarantine(quarantine/release)`、`hub_consolidate(apply)`、`hub_trigger(add/enable/disable/del/fire)`、`hub_export(prune + apply=true)`、替他人 `hub_agent(control/skills)`。以下**不拦**：读自己角色、日常写、`hub_export` 只读预演、管自己的 control/skills。

拒绝文案会给出授权命令；同类越权每进程只写一条 `journal`（`action=越权拦截`），避免循环调用刷爆审计。查最近拦截：

```bash
python cli.py audit-export --format csv --days 1
```

**任务持有权的第二道闸（R80）**：`hub_task_update` / `hub_task_retry` / `hub_task_approve` 的「空 agent=管理面」旁路只在 CLI/GUI/REST 生效。MCP 会话没锁定 `--agent` 且没传 agent 时直接拒收——否则匿名客户端可以完成、交办甚至审批别人的任务。持有者署名可正常流转；manager 角色不额外获得替他人关单的特权，批量善后走管理面。

回滚：把相关 agent 切回 `worker` 即可，不动数据；角色列由 schema 迁移自动补齐，旧库无需手工改表。

### 10.7 记忆与记录归属：谁能改写/取代（R81）

知识共享，但条目有作者。`hub_memory_write` 的**新增**（append）不受限；一旦动**既有条目**，要过归属闸：

| 动作 | 谁能做 |
|---|---|
| 新增记忆 | 任何已接入 agent（未锁身份的普通写入也可，归属记入实际身份） |
| 改写自己的记忆（`mode="overwrite"` / `supersedes`） | 作者本人、manager、管理通道 |
| 改写/取代他人的记忆，或用 `feedback="archive"` 下架他人记忆 | 仅 manager 或管理通道 |
| 裁决两条记忆/记录（`hub_memory_supersede`） | 条目全归自己、manager、管理通道 |
| 整理无主历史条目（agent 为空 / unknown / user / migrated） | 任何已锁身份的 agent |

- MCP 会话未锁 `--agent` 时，只要触碰**有主条目**就拒——clientInfo 不能证明归属；纯新增仍可用。
- 拒绝会写 journal `action=越权拦截`（同类每进程一次防刷），提示里点名条目 id 与作者；合法归档写 `action=memory_archive`。
- `helpful / not_helpful / stale / wrong` 是投票，不改归属；只有 `archive` 会下架，因此单独过闸。
- 坏 `supersedes` id 现在返回 permanent 错误，不再抛 ValueError，也不会悄悄新增一条。
- 回滚：移除 `_memory_ownership_gate` 与 `call_tool` 里的调用点即可；brain 层没有加限制，CLI/GUI/REST 直调行为不变。

### 10.8 撤销与复核：必须有可核验身份（R82）

`hub_undo` 按 agent 参数撤记录、`hub_memory_confirm` 重置记忆新鲜度——两者都依赖「谁在动」，没有可核验身份的会话不能做：

| 操作 | 未锁 `--agent` 的 MCP 会话 | 锁定会话 | 管理通道（CLI/GUI/REST） |
|---|---|---|---|
| `hub_undo` | 拒收 | 只能撤自己（`agent` 参数被进程身份覆盖） | 可撤指定 agent 的最新记录 |
| `hub_memory_confirm` | 拒收 | 可复核任意记忆（协作信号，不是改写） | 放行 |

- 拒收提示要求用 `--agent` 启动或改走管理面；`journal` 写 `action=越权拦截`，note 含 `R82`（同类每进程一次防刷）。
- 锁定会话传别人的 `agent` 不报错，但会被启动身份覆盖并留 `agent_mismatch` 痕；撤销目标始终是自己。
- 回滚：移除 `_unverified_write_gate` 与 `call_tool` 里的调用点；brain 层未加限制，管理通道行为不变。

### 10.9 任务与租约写动作：同样必须署名（R83）

`hub_claim`、`hub_checkpoint(action="save", task_id=…)`、`hub_lock(action="acquire/renew/release")`、`hub_handoff(action="create/claim")` 都会把传入的 `agent` 当操作者写入归属。未锁身份的 MCP 会话传任意名字即可冒名认领任务、写他人检查点、续/放他人租约、创建或认领交接：

| 工具 / 动作 | 未锁 `--agent` 的 MCP 会话 | 锁定会话 | 管理通道（CLI/GUI/REST） |
|---|---|---|---|
| `hub_claim` | 拒收 | 按进程身份认领（传入 `agent` 被覆盖） | 可替指定 agent 认领 |
| `hub_checkpoint` action=save（缺省） | 拒收 | 放行（brain 仍校验任务持有者） | 放行 |
| `hub_checkpoint` list/latest | 放行 | 放行 | 放行 |
| `hub_lock` acquire/renew/release | 拒收 | 放行（brain 仍校验租约归属） | 放行 |
| `hub_lock` check/list/prune | 放行 | 放行 | 放行 |
| `hub_handoff` create/claim | 拒收 | 放行 | 放行 |
| `hub_handoff` list | 放行 | 放行 | 放行 |

- 只拦「写动作」，只读查询保持匿名可用——未接身份的接入仍能查看检查点时间线、租约台账与交接清单。
- 拒收写 `journal action=越权拦截`，note 含 `R83`（同类每进程一次防刷）；锁定会话传别人 `agent` 会留 `agent_mismatch`，实际归属仍是进程身份。
- 回滚：把 `_UNVERIFIED_WRITE_TOOLS` 里 R83 的四个条目删掉即可恢复旧行为；闸门函数本身保留给 R82 使用。

### 10.9b 追加型写入：不许自报他人在册身份（R101）

`hub_log_work` / `hub_report_error` / `hub_env_set` / `hub_event_write` / `hub_memory_write` / `hub_heartbeat` / `hub_task_add` 这类**追加型写入**把传入 `agent` 当归属，而 `check_agent` 只验「名字在册」不验「身份真实」——未锁 `--agent` 的会话自报 `agent="zcode"` 就能把记录/错误/记忆/心跳记到别人名下，污染归属视图与 `hub_undo` 边界。与前几轮整工具拒收不同，这些写入**没有 agent 也应可用**（`unknown` 归属、CLIENT_NAME 补写是设计内路径），所以只拦「自报在册名」：

| 调用 | 未锁 `--agent` 的 MCP 会话 | 锁定会话 | 管理通道（CLI/GUI/REST） |
|---|---|---|---|
| `agent=<在册名>` | 拒收（记「越权拦截」，note 含 `R101`） | 放行（被进程身份覆盖） | 放行 |
| `agent=unknown` / 空 / user / migrated | 放行（无主语义） | 放行 | 放行 |
| `agent=<不在册名>` | `check_agent` 原路径报错（不进 R101 拦截） | — | — |

- 拒收文案给两条出路：`--agent <名>` 重新接入，或 `agent="unknown"`（仅确属无法归属时使用）。
- 回滚：删除 `_APPEND_WRITE_TOOLS` 与 `call_tool` 里的 `_append_identity_gate` 调用点即可恢复旧行为。

### 10.10 通信署名：发信与回执都要可核验（R84）

`hub_signal_send` 的发送者、`hub_signal_read` 的已读回执都写传入 `agent`。未锁身份的 MCP 会话可以冒名发信（误导对方、触发自动化），也可以替他人标已读（伪造回执、把消息从对方收件箱里抹掉）：

| `hub_signal_send` | 拒收 | 发送者被进程身份覆盖 | 可代指定 agent 发送 |
| `hub_signal_read` | 拒收 | 放行；brain 仍校验收件人（点对点非收件人勿动，广播谁都能标） | 可代标 |
| `hub_signals`（收件箱）/ 信号列表 | 放行 | 放行 | 放行 |

- 拒收写 `journal action=越权拦截`，note 含 `R84`（同类每进程一次防刷）。
- 回滚：删掉 `_UNVERIFIED_WRITE_TOOLS` 中 R84 的两个条目；brain 层与收件箱读取不变。

### 10.12 越权拦截可观测（R90）

拒绝动作一直有审计痕（`journal action=越权拦截`），但散在流水里，管理者要回答「谁在冒名、哪个工具被反复尝试」只能手翻。现在：

```text
hub_status(view="security")                 # 默认近 7 天
hub_status(view="security", days=30)        # 近 30 天
```

- `brain.security_snapshot` 按工具归并，区分**未锁身份**（`tool:identity`，MCP 会话没带 `--agent`）与**角色越权**（worker 尝试管理动作/跨归属改写）；窗口外与不可解析时间不计，不猜。
- 输出含每工具次数、最近一次时间、最近 5 条拦截（agent 多为 `unknown`）与处置建议；`team_digest` 增 `current.security` 和 `security_denied` 风险，CLI `digest` 的当前行在有拦截时显示「拦截 N」。
- **只读**：查看不产生新流水，也不改任何状态。
- 处置顺序：先给 MCP 接入补 `--agent <名>`；确实需要管理动作的 worker 由管理面授 `manager`；一次性管理操作走 CLI/GUI 管理通道。
- 注意去重：同类拒绝每进程只记一次（防循环调用刷爆 journal），所以「次数」是**会话级首次**计数，不是每次尝试的精确次数。
- 查询性能（R91）：`idx_journal_action_ts(action,ts)` 支撑安全视图与日结，`idx_journal_ts(ts)` 支撑审计窗口，`idx_handoffs_status(status)` 支撑交接查询；存量库 `init_db` 自动补建，无需手工迁移。

## 11. 规则闸门：证据通道与探针（R32/R63）

「干完活必须落大脑」由各家 agent 的 hook 守卫强制执行，`rules_health` 巡检它是否真在位、真在跑。**三家机制、两种证据通道，别拿一把尺子量**：

| agent | 闸门机制 | 触发证据通道 |
|---|---|---|
| workbuddy | `guard-brainlog.mjs`（present_files 交付闸门） | 守卫日志 |
| claude / codex / qoder / dsh | `agent_guard.mjs`（Stop 事件硬阻断，最多 2 次防死循环） | 守卫日志 |
| hermes / hermes-cn | `agent_guard.mjs`（平台不支持收工硬拦：pre_tool_call 校验 + pre_llm_call 软提醒） | 守卫日志 |
| zcode | `auto_log.py`（会话轨迹自动捕获，写 `source='auto'` 的大脑记录） | **auto 记录**（不是守卫日志） |

- 通道声明在 `~/.agenthub/hooks/targets.json` 每目标的 `evidence` 字段（`guard` 缺省 / `auto_records`）。
- 「配置在位但零触发」分两类（R32）：**dead** = 该 agent 近 14 天有工作记录却零触发 → 钩子疑似失效，计硬缺口；**idle** = 无活动 → 只是未获验证。大脑读不到活动数据时不猜，按未验证处理。
- **契约级实测**（R63）：`python tools/gate_probe.py` 按各 agent 的 hook 事件词汇表（hermes 系小写下划线 `session_start`/`pre_tool_call`/`subagent_stop`，dsh 用 Claude 标准名）构造与生产同形的载荷实跑守卫，验证放行路径（reset / marked logged / gate allowed）与阻断路径（worked 未记大脑 → `decision:block`），回读日志核对归因。**边界**：它证明「钩子接了线、灯会亮」，不证明各家 Runner 真会按此形态调用——端到端要等一次真实会话。探针写的日志行（`sid=probe-*`）不计入触发证据。
- 逃生门：`ASU_SKIP_BRAINLOG=1`（跳过即写审计日志，可追责）；任何异常守卫一律放行（fail-open），绝不阻塞正常会话。
- 修一条静默闸门：先 `python tools/gate_probe.py` 做契约实测；契约过而真实会话仍不触发，再核对该 agent 的 hook 配置是否真的加载（重启客户端）。

## 12. 信号协作总线与陈旧治理（M3 / R77）

`hub_signal_send` 发消息（`to_agent` 留空=广播），对方下次心跳自动收到未读提醒，`hub_signal_read` 标已读（按人各记一次，广播才有全员回执）。与 `hub_events` 分工：signal=需消费的消息（有回执），events=只增事件流。

**陈旧治理（R77）**：一条没人读的信号原本会在每次心跳里原样再推一遍、永远占着未读名额（`signal_reads` 全表 0 行时尤其明显），越积越多后「N 条未读」本身就变成噪音，还会把 `limit=2` 里真正新的信号挤掉。现在超过 `SIGNAL_STALE_DAYS`（7 天）仍未读的：

- 开工推送**不再逐条给内容**，只给一句「[未读信号·陈旧] N 条超过 7 天仍未被读」；
- 收件箱 `hub_signals` 仍可见并标「（陈旧）」——**不静默丢弃**；
- **不自动标已读**：那等于伪造送达回执；回执只由收到的人显式 `hub_signal_read` 产生。

清理：确认内容已过期就 `hub_signal_read` 归档；内容仍有效就重发一条新的（新的才进开工推送）。

### 13.1 采集与探针的两条硬规矩（R240/R241 各吃过一次）

- **分段懒加载的页，采集前必须先把各段兑现**。治理中心八段现在只刷屏幕上那一段（整页刷新 464ms→3ms），所以 `tools/gui_snapshot.py` 与区块图标守卫都先调 `page.reveal_all_segments()` 再采集。守卫若不改，报的不是「产品回归」而是基线自己退化成只守首屏——**别拿 `--update` 了事**，重建基线正是把守卫削短的那个动作。同一条款下的数据口径：看不见的段允许旧，**屏幕上那一段永远不旧于最近一次治理写入**（写过库的刷新会把兄弟段全标回待重读；纯读——切段补读、筛选开关——不标脏，否则来回切段每次全重读，336ms 的安全段会被反复付）。
- **离屏（`QT_QPA_PLATFORM=offscreen`）实例关窗什么都不许写**。探针和工具不经 pytest，就躲得过 R232 那条「pytest 环境兜底」：R240 实测一次离屏探针 `win.close()` 把用户 `~/.agenthub/config.json` 里的窗口几何覆盖成离屏尺寸，旧值无备份不可恢复。现在判据抽成 `window._close_hooks_quiet(env, skip_flag)`——离屏即静默，脚本作者**不需要记得**设 `_skip_close_hooks`。写探针前先读这条；用户配置和真实大脑不是试验田。
